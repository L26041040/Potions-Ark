## 給 Claude Code 的指令

你要實作「Potions 二店選址倉庫」：Potions Magic Bar 的股東們共用的二店候選物件倉庫。這是 3 到 6 人使用的小型內部網站，目標是最快交付可用版本。

### 一、動工前先讀

依序讀完再寫程式：

1. `GLOSSARY.md`：名詞表。畫面文字與提交訊息都用這裡的名詞，不用它列為避免的同義詞。程式代號的對應寫在規格 B3（物件一律叫 `item`）。
2. `docs/adr/`：三份決策紀錄。不要推翻；若實作上發現行不通，停下來回報。
3. `docs/spec/mvp-spec.md`：規格。B 部分是技術架構，C 部分是驗收標準（AC1–AC34），D 部分是順序。
4. `docs/spec/appendix-591.md`：591 的網址形狀、可取得的欄位、正規表示式與測試案例。寫去重鍵與 591 解析時照這份。
5. 安裝 Next.js 之後，寫任何 Next.js 程式之前，先讀 `node_modules/next/dist/docs/` 裡與你要寫的功能相對應的文件。這個版本與舊版差異很大，不要憑記憶寫。

### 二、三條原則

1. 二店選址是唯一主軸。任何流程都不得要求填寫展演相關資訊。
2. 看照片與共同討論優先。照片要出現得快，討論要寫得順。
3. 規格沒寫的功能不做。規格 B8 列出的項目明確不做。想加任何東西之前先問。

### 三、權限邊界

超出大哥這次給的授權範圍時，**不得**做以下任何一件事：

- 建立 Vercel 專案、資料庫、Blob store，或主動觸發部署。
- 建立或推送 `main` 分支。開發只在這次工作階段指定的開發分支上進行。
- 開 pull request。

以下幾件事不論授權範圍，一律不做：

- 升級方案、購買任何東西、變更 repo 可見性。
- 設定、讀取或索取 Vercel 上的 `SITE_PASSWORD`。這個變數永遠由大哥在 Vercel 後台輸入。本機環境檔裡的測試密碼不在此限。
- 登入已部署的站，或在已部署的站上建立資料。

專案連上 Vercel 之後，推送開發分支會自動產生預覽部署，這不算違反上述規定。

程式庫是公開的。不得提交密碼、`.env` 檔、真實物件資料。測試用的網頁樣本必須是你自己手寫的精簡片段（只含需要的 meta 標籤與 JSON-LD，數值用虛構的），不得整頁複製第三方網頁。

### 四、技術基線

以規格 B 部分為準，以下是最容易做錯的幾點：

- **建立專案**：repo 根目錄已有其他檔案，`create-next-app` 會拒絕直接在根目錄建立。在暫存子資料夾建立後把檔案搬到根目錄。使用 TypeScript、Tailwind、App Router、ESLint、npm。旗標以當下 `create-next-app --help` 為準。
- **Cache Components**：若腳手架預設開啟，先照它的規則寫（讀 cookie 與資料庫的伺服器元件包在 `<Suspense>` 內，不使用 `'use cache'`）。若它卡住進度超過一次嘗試，直接在 `next.config` 關掉，不要耗時間。
- **驗證**：`proxy.ts` 只負責把未登入的頁面請求導向登入頁。真正的把關是 `verifySession()`，每一個 Server Action、Route Handler、讀資料的伺服器元件第一步都要呼叫。Server Action 是任何人都能直接 POST 的端點。
- **分工**：小型寫入用 Server Action。照片上傳與匯入用 Route Handler（Server Action 本文上限 1 MB，且同一瀏覽器一次只送一個）。
- **資料庫**：`pg` 連線池，延遲建立（import 時不連線）。全部用參數化查詢。Schema 只增不減，寫成 PostgreSQL 16 相容。
- **照片**：只有 `lib/storage.ts` 可以引用 `@vercel/blob`。寫入一律公開、加隨機字尾、路徑由伺服器產生、明確指定內容型別。用哪種儲存的判斷條件照規格 B5，在 Vercel 上沒有 Blob 變數時要報錯。不得為了本機測試而加入長期有效的 Blob 權杖。
- **網址狀態**：面板與大圖的開關只由網址查詢參數推導，用 `history.pushState`／`replaceState` 配合 `useSearchParams`。不要用 parallel routes 或 intercepting routes。傳給 `pushState` 的 state 一律是新物件，不要把 `window.history.state` 原樣傳回。
- **資料呈現**：主頁一次載入全部物件、照片清單、討論紀錄。用戶端元件直接用 props 渲染，不要把伺服器資料複製進 `useState`，否則更新後畫面不會變。尚未送出的草稿依物件另外存在用戶端記憶體。
- **純函式獨立**：去重鍵、取網址、解析、session 簽章、檔頭檢查、抓取位址檢查寫成不依賴 Next.js、資料庫、Blob 的純模組，才能直接做單元測試。
- **抓取**：照規格 B6「抓取安全與禮貌」。遇到 403、429、202 或驗證挑戰就停，絕不嘗試繞過。抓取函式做成可注入的；正式程式不得有任何放行本機位址的開關。
- **時間**：畫面上的時間一律以台北時間顯示，不要用伺服器的時區。

### 五、本機驗證方式

開發機拿不到 Neon 與 Blob 的憑證，所以：

- 資料庫用本機 PostgreSQL（開發機已安裝 16 版，需自行啟動）。若沒有，選一個不需要雲端憑證的替代做法並在回報中說明。
- 照片用 `lib/storage.ts` 的本機磁碟模式。
- 用一個只存在本機環境檔（不提交）的測試密碼登入。
- 匯入的自動化測試不經網路：直接呼叫匯入函式並注入假的抓取，回傳你手寫的樣本，包含 591 主機名與短連結的轉址鏈。抓取位址檢查另外用單元測試驗。不要在自動化測試裡連真實的 591。
- 對真實 591 的確認只做一次、手動、在本機、貼一個店面出租網址，並在回報裡寫明結果。
- 寫一支瀏覽器冒煙腳本 `scripts/smoke.cjs`，使用開發機預先安裝的 Playwright，不要另外安裝。預裝的 Playwright 只能用 `require` 載入，所以檔案用 `.cjs`。腳本對本機伺服器走一遍：
  - 登入、手動新增、上傳照片、開面板、開大圖、返回鍵依序關閉。
  - 上一間／下一間、改狀態、編輯目前結論、留言。
  - 貼一個會被擋下的網址（例如 `http://localhost/x`），確認物件仍然建立而且可以補填。
  - 同一個網址再貼一次，確認開啟的是既有物件。
  - 刪除、從回收桶還原。
  - 階段二再加上列表切換、搜尋、排序。

### 六、執行順序

照規格 D 部分的順序，一次做一步，每步做完自己驗證再往下：

- **階段零**：D1 的三步。
- **階段一**：D2 的八步。
- **階段二**：D3 的四步。

每一步完成後提交一次，提交訊息說明做了什麼與為什麼，並推送到開發分支。

每個階段結束時的關卡，全部通過才算完成：

1. lint、型別檢查、單元測試、建置全部通過。
2. 冒煙腳本通過。
3. 該階段對應的驗收標準逐條確認，並在回報中列出每一條是「通過」「未通過」或「需要正式環境才能驗」。標為需要正式環境的項目不擋階段完成。

不得為了過關而跳過、停用或刪除測試。

### 七、部署

只有授權範圍包含部署時才做，步驟照規格 D4。其中標示「大哥」的步驟你做不了，要停下來清楚告訴大哥該點哪裡、填什麼，等大哥回覆完成後再繼續。

你不登入正式站。部署後請大哥依 D4 步驟 9 貼一個真實的 591 店面網址並告訴你面板顯示了什麼；你再對照執行紀錄確認正式環境抓得到，把結果寫進回報。

### 八、遇到狀況怎麼辦

- 規格與實際行為衝突（例如平台限制變了、某個做法在這個版本行不通）：選最簡單、不擴大範圍的替代做法，做完在回報中說明改了什麼與為什麼。
- 會改變大哥已定案決議的事（規格 A2 的表與 B8 的清單）：停下來問，不要自己決定。
- 需要大哥操作才能繼續：一次把需要的步驟講清楚，不要分好幾次問。

### 九、每個階段結束的回報

用繁體中文，內容包括：

1. 完成了什麼，對照驗收標準編號。
2. 每一條驗收標準的結果。未通過或無法驗證的要說明原因。
3. 與規格不同的地方，以及理由。
4. 需要大哥操作或決定的事項，一次列完。
5. 已知問題與尚未驗證的部分，照實寫。
