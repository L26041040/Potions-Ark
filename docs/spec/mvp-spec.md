## A. 最終設計結論

### A1. 定位

股東共用的二店候選物件倉庫：貼上刊登網址或手動新增物件，大家看照片、改狀態、寫下目前結論、留下討論紀錄。

三條不可違反的原則：

1. **二店選址是唯一主軸。** 展演只是部分物件可能的複合規劃。任何流程都不得要求填寫展演相關資訊，「規劃」永遠是選填。
2. **看照片與共同討論優先。** 圖庫、列表、篩選、詳細面板的每個取捨，都以「照片出現得快、討論寫得順」為先，其他資訊退到次要位置。
3. **最快交付，不為理論上的完善加工程。** 本文件沒寫的功能就不做。

### A2. 已定案的決議

| 主題 | 決議 |
|---|---|
| 形式 | 客製化網站，不用 Notion。目標是最快做出可分享的網站，不承諾完成時間。 |
| 資料與照片 | Neon Postgres ＋ Vercel Blob（公開 store，網址不可猜）。見 ADR-0002、ADR-0003。 |
| 進出 | 一組共享密碼＋自填暱稱，沒有個人帳號，沒有免密碼邀請連結。見 ADR-0001。 |
| 登入保存 | 登入狀態保存 90 天；更換共享密碼後所有裝置自動失效。 |
| 新增物件 | 貼網址（匯入）與手動新增兩條路。匯入失敗也一定建立物件，再補填。 |
| 去重 | 同一來源網址只能有一個物件；比對前先正規化網址、忽略追蹤參數。 |
| 照片 | 上傳前在瀏覽器壓縮；匯入時把刊登照片複製進自己的儲存，不外連。 |
| 狀態 | 固定四種：未討論、待確認、不考慮、確定考慮。任何股東可直接改。 |
| 目前結論 | 每個物件一段可隨時編輯的文字。 |
| 討論紀錄 | 依時間排列的留言（暱稱＋時間），狀態異動自動記入同一條時間軸。 |
| 刪除 | 軟刪除進回收桶，可還原。 |
| 詳細面板 | 桌面右側 50%、手機全螢幕；照片輪播、全螢幕大圖、上一間／下一間；X、Esc、瀏覽器返回鍵都能關。 |
| 直達連結 | 每個物件有可分享的直達連結；未登入者仍須先輸入共享密碼。 |
| 檢視 | 圖庫（預設）與列表，共用篩選、搜尋、排序；預設不顯示「不考慮」。 |
| 樓層 | 一個多行文字欄「樓層與用途」，不建樓層表。 |
| 規劃 | 選填單選：純二店／二店＋展演／未定。只顯示，不做篩選。 |
| 重複刊登 | 不合併。一個物件對應一則刊登，發現重複由股東自行刪除。 |
| 交付 | 分兩階段；階段一就包含貼網址新增。最終驗收項目不因分階段而減少。 |

### A3. 查證後需要大哥知悉的四件事

這四件不是新問卷，規格已各自採用下述預設；若要改，請在正式授權時一併說明。

1. **Vercel Hobby 不能明確算合規，規格預設採 Vercel Pro 單一席位。**
   - 服務條款第 4 條（2026-10-19 版）原文：「You shall only use the Services under a Hobby plan for your personal or non-commercial use.」
   - Vercel 目前已不再公布「商業用途」的定義，對「營利事業的內部工具」也沒有官方答覆。本工具是營利事業的內部商業工具，屬灰色地帶且偏向不合規。同一條款允許 Vercel 不經通知停用 Hobby 專案。
   - Pro：US$20／月（未稅），內含 1 個部署席位與 US$20 用量額度。股東只是開網址，不需要 Vercel 帳號也不佔席位。本專案規模的用量預期落在內含額度內。
   - 目前帳號是哪個方案，工具讀不到，推測是 Hobby；請大哥在 Vercel 後台 Settings › Billing 確認。
   - 開發與自測可在現有方案上進行；**放入真實物件、交給股東使用之前**升級。升級是購買行為，只能由大哥本人操作。
   - 不想付費的替代方案（Netlify 免費版、Cloudflare）都要改寫儲存層，多出半天到兩天工程，與最快交付相違，故不採用。
2. **GitHub repo 目前是公開的。** 規格、名詞表任何人都看得到。規格規定程式庫內不得放密碼與真實物件資料，所以公開不會洩漏資料；但這是公司內部的展店規劃，建議改為私人（GitHub › Settings › General › Danger Zone，只有大哥能改）。
3. **591 頁尾有禁止自動下載的聲明。** 原文：「亦不得使用網路爬蟲或其他自動下載程式或任何其他類似或具相同功能的手動程序來連續自動搜索、獲得、使用、下載，如有違反……本公司將收取一個刊登物件內容，三千元計算之費用」。591 的 robots.txt 本身不禁止抓取。
   - 規格預設維持大哥的決議（匯入時複製照片），並把行為限制在最窄：只在股東貼上網址時抓那一頁一次，不排程、不重抓清單、不繞過任何防護。
   - 這是否可接受屬於法律與商業判斷，小的無法代為認定。較保守的選項是「591 只存連結與文字、照片由股東截圖上傳」，改動很小。
4. **591 以外的網站大多抓不到。** 實測十家房仲站：樂屋、永慶、台灣房屋擋機器，太平洋是前端渲染抓不到內容，信義與 21 世紀可抓到標題，其餘四家當天沒測到有效刊登。所以「貼網址→建立物件→手動補填與上傳照片」是 591 以外的主要流程，必須順手。

## B. 最終技術架構

### B1. 技術選型

| 項目 | 選擇 |
|---|---|
| 框架 | Next.js（App Router）＋ TypeScript。以動工當下 `create-next-app` 的最新穩定版為準（查證日為 16.4.6）。 |
| 樣式 | Tailwind CSS（查證日為 v4，CSS-first 設定）。不引入 UI 元件庫。 |
| 主機 | Vercel，Functions 區域 `sin1`（新加坡），與資料庫同區。 |
| 資料庫 | Neon Postgres，經 Vercel Marketplace 安裝，Free 方案，新加坡區域。一個資料庫。 |
| 資料存取 | `pg` 連線池＋參數化 SQL。不用 ORM，不用 migration 框架。 |
| 照片 | Vercel Blob，一個公開 store，區域 `sin1`。 |
| 測試 | Vitest，只測純函式；另有一支瀏覽器冒煙腳本。 |

該版本 Next.js 與舊版差異大（查證日：攔截檔是 `proxy.ts` 而非 `middleware.ts`；`cookies()` 等是非同步；Server Action 是公開端點、本文上限 1 MB）。實作前先讀 `node_modules/next/dist/docs/` 的對應文件，不憑記憶寫。

### B2. 部署方案

- 正式站：Vercel Pro、一個席位（理由見 A3 第 1 點）。Deployment Protection 維持預設的 Standard Protection：正式網址公開、由本站自己的共享密碼把關；預覽網址需要 Vercel 登入，只有大哥與開發代理看得到。
- 正式分支是 `main`。開發在 `claude/optimistic-gates-9v9rmn`，通過階段驗收的版本才推進 `main`。`main` 必須在建立 Vercel 專案**之前**就存在，否則 Vercel 會把開發分支當成正式分支。
- 一個 Neon 資料庫，連到 Production 與 Preview（後台預設值），不啟用 Preview Branching。預覽部署因此讀寫同一份資料，只用於開發驗證，測試資料用完即刪。
- 全站回應帶 `X-Robots-Tag: noindex, nofollow`，並設定頁面 metadata 的 robots 為不索引。
- 環境變數只有一個需要人工設定：`SITE_PASSWORD`。資料庫與 Blob 的變數由 Vercel 在連接時自動注入。
- 程式庫內不得出現密碼、`.env` 檔、真實物件資料。提供只列變數名稱的 `.env.example`。

部署步驟見 D4。

規則：

- Schema 寫在單一檔案 `db/schema.sql`，可重複執行、只增不減（`CREATE TABLE IF NOT EXISTS`、`ADD COLUMN IF NOT EXISTS`、`CREATE INDEX IF NOT EXISTS`）。由 `scripts/db-setup.mjs` 在建置指令中套用：`node scripts/db-setup.mjs && next build`。在 Vercel 上若沒有資料庫連線字串，腳本必須失敗；在本機沒有時略過並警告。
- 執行期用 `DATABASE_URL`（連線池），schema 腳本用 `DATABASE_URL_UNPOOLED`。SQL 寫成 PostgreSQL 16 相容。
- 不加任何定時連資料庫的保活或排程。

### B4. 進出控制

- 環境變數 `SITE_PASSWORD`。未設定或少於 8 個字元時，一律拒絕登入（封閉式失敗）。建議 12 個字元以上。
- 登入頁只有兩個欄位：共享密碼、暱稱（1–20 字）。
- 登入成功後設定兩個 cookie，都是 `httpOnly`、`secure`、`sameSite=lax`、有效 90 天：
  - `ark_session`：以 `SITE_PASSWORD` 為金鑰、對固定字串做 HMAC-SHA256 的結果。伺服器用定時安全比較驗證。換密碼並重新部署後，舊 cookie 自動失效，不需要第二個密鑰。
  - `ark_nick`：暱稱。
- 驗證做兩層：
  - `proxy.ts`：沒有有效 cookie 的頁面請求，導向 `/login?next=<原路徑與查詢字串>`。`next` 只接受以單一 `/` 開頭的站內路徑。
  - `verifySession()`：每一個 Server Action、每一個 Route Handler、每一個讀資料的伺服器元件，第一步都要呼叫。失敗回 401 或導向登入。
- 未登入時的任何回應，都不得包含物件資料或照片網址。
- 密碼錯誤時回一般性錯誤訊息並延遲約半秒。不做鎖定機制。
- 股東可在選單改暱稱（更新 cookie）；舊留言保留當時的暱稱。可登出。

### B5. 照片

**儲存**

- 一個公開 Blob store。每次寫入都用伺服器產生的路徑，並加上隨機字尾，不使用原始檔名。路徑以環境區分：正式環境 `prod/…`，其餘 `dev/…`。
- 所有 Blob 存取集中在 `lib/storage.ts`（只匯出存、刪兩種操作），其他檔案不得直接引用 `@vercel/blob`。沒有 Blob 環境變數時，改用本機磁碟（只供開發與測試），讓開發機不需要任何雲端憑證。
- 已知取捨：拿到某張照片網址的人不需共享密碼就能看到那一張；換密碼不會讓照片網址失效，刪除照片才會。上傳介面提示「請勿上傳合約、證件等機密文件」。

**股東上傳**

- 瀏覽器先壓縮：長邊不超過 1600px 的 JPEG，目標每張 600 KB 以下。壓縮後仍超過 4 MB 就再降品質；瀏覽器無法解碼的格式顯示錯誤，不送出原檔。
- 一次請求只傳一張（Vercel 單次請求上限 4.5 MB），用 Route Handler 接收，不用 Server Action。前端同時最多傳 3 張，逐張顯示進度，失敗可單張重試。
- 伺服器檢查：已登入、物件存在且不在回收桶、大小不超過 4 MB、檔頭確實是 JPEG／PNG／WebP、該物件照片未達上限。
- 每個物件照片合計最多 50 張。

**匯入照片**

- 匯入時由伺服器下載刊登照片並存入 Blob，最多 20 張，同時最多 4 張。任何一張失敗都跳過，不影響物件與其他照片。
- 只接受 JPEG／PNG／WebP／GIF／AVIF（同時檢查 Content-Type 與檔頭），單張上限 8 MB。照原樣儲存，不重新編碼。
- 同一物件已有相同 `source_photo_url` 的照片就不再複製。
- 通用匯入取得的 `og:image` 若已掛在同網站的其他物件上，視為網站預設圖，不匯入。
- 匯入完成後，畫面上的照片一律來自自己的儲存，不直接連到刊登網站。

**顯示**

- 圖庫與列表的封面用縮圖（`next/image`，來源限定為本 store 的主機名，寬度檔位限制在兩三種）。面板輪播與全螢幕大圖直接用 Blob 原圖。縮圖額度出問題時，設定 `images.unoptimized` 是一行退路。
- 所有照片 `loading="lazy"`，用已知寬高預留版位。
- 封面是 `sort_order` 最小的照片；「設為封面」就是把它排到最前。
- 刪除單張照片需確認，確認後永久刪除（同時刪 Blob）。物件進回收桶時不刪任何照片。

### B6. 網址匯入與去重

**流程**

1. 股東在輸入框貼上內容（可夾雜文字）。伺服器取出第一個網址；網址以外的文字當作暫定名稱。
2. 計算去重鍵 `url_key`（規則見下）。591 的短分享連結要先跟隨轉址才知道物件編號。
3. 以 `url_key` 查既有物件（含回收桶）：
   - 已存在且未刪除：不新增，直接開啟該物件並提示「這個物件已經在倉庫裡」。
   - 在回收桶：詢問「此物件在回收桶，要還原嗎？」。
   - 不存在：立即建立物件。名稱用暫定名稱；沒有就用「來自 <網站主機名> 的物件」。兩人同時貼同一網址時，靠唯一索引只留下一個。
4. 畫面馬上出現新物件並開啟面板，同時在背景呼叫匯入端點。
5. 匯入端點抓取該頁一次、解析、只**補空白欄位**（名稱只在仍是自動產生的預設名稱時才取代），再複製照片，回傳結果摘要。
6. 面板顯示結果：成功時列出帶入了什麼；失敗或部分成功時顯示原因（例如「此網站不允許自動擷取，請手動補填」），並直接進入編輯。
7. 有來源網址的物件可按「再試一次」重跑第 5 步。它只補空白欄位與尚未存在的照片，絕不覆蓋股東已填的內容。

**去重鍵規則**

- 取網址：從貼上文字找第一個 `http(s)://` 開頭的片段，遇到空白或全形標點即結束，去掉結尾的半形標點。
- 591：鍵為 `591:<rent|sale|ding>:<物件編號>`，忽略主機名與所有查詢參數。需涵蓋的網址形狀：
  - `business.591.com.tw/rent/<id>`、`business.591.com.tw/sale/<id>`
  - `rent.591.com.tw/<id>`、`rent-detail-<id>.html`（rent、www、m 三種主機）
  - `m.591.com.tw/v2/rent/<id>`、`m.591.com.tw/v2/business/rent/<id>`（sale 同理）
  - `store.591.com.tw/ding-detail-<id>.html`（頂讓，獨立的編號序列）
  - 路徑以 `/mobile-detail.html` 結尾且帶 `houseId=R|S|D<id>`
  - 短分享連結（591 主機、路徑為 1–8 個英數字、帶 `salt` 參數）：手動跟隨轉址，最多 5 次，每一跳都必須是 https 且主機為 `591.com.tw` 或其子網域，對每個轉址目標套用上述規則；解析不出來就退回通用規則。
- 591 的 `source_url` 一律存重組後的標準網址，不保存 `s`、`salt` 等分享參數（可能帶有分享者身分）。
- 其他網站（通用規則）：
  1. 只接受 `http`、`https`，且網址不得帶帳號密碼；否則不產生鍵（物件仍然建立）。
  2. 鍵不含協定；主機名轉小寫並去掉開頭的 `www.`；省略預設連接埠。**不**去掉 `m.` 之類的前綴。
  3. 路徑保留大小寫，去掉結尾的 `/`。
  4. 查詢參數：刪除追蹤參數後，其餘**全部保留**並依名稱排序。許多房仲站把物件編號放在查詢參數（樂屋 `ehid`、住商 `sn`、太平洋 `saleID`），所以不在刪除名單上的參數一律不能動。
  5. 刪除名單（不分大小寫）：`utm_` 開頭的全部，以及 `fbclid`、`gclid`、`gbraid`、`wbraid`、`dclid`、`msclkid`、`yclid`、`twclid`、`ttclid`、`igshid`、`igsh`、`mibextid`、`mc_cid`、`mc_eid`、`_ga`、`_gl`、`srsltid`、`openExternalBrowser`、`openInAppBrowser`。
  6. 去掉 `#` 之後的片段，除非以 `#/` 或 `#!/` 開頭。
- 不做第二把鍵（不拿 `rel=canonical` 或 `og:url` 再比一次）、不做其他房仲站的專用規則。已知後果：同一刊登若有兩種完全不同的網址形狀，可能建出兩個物件，由股東自行刪除其一。

**解析**

- 通用（階段一）：名稱取 `og:title`，沒有就取 `<title>`；物件描述取 `og:description`，沒有就取 meta description；照片取 `og:image` 一張。
- 591 進階（階段二），適用 `business.591.com.tw` 的租售頁：
  - 優先讀 JSON-LD，再讀 meta，不解析頁面內嵌的 `__NUXT__` 資料。
  - 名稱、月租金、地址、地區、樓層取自 JSON-LD；坪數取自描述句（JSON-LD 沒有）；押金取自頁面文字，原文存入「押金／其他費用」。
  - 照片取 JSON-LD 的 `image` 陣列，只留 `/house/年/月/日/` 路徑的圖，依路徑去重，照頁面給的網址原樣下載。
- 591 住宅頁與頂讓頁資訊不全，走通用解析即可，不另寫專用規則；頂讓頁的照片由股東手動上傳。
- 每一條解析規則都要「抓不到就留空」，不得因為某欄解析失敗而讓整次匯入失敗。

**抓取安全與禮貌**

- 只有已登入的股東能觸發；一次貼上只抓一頁，不自動重試、不排程、不抓列表頁。
- 只接受 `http`、`https`；拒絕 IP 位址形式的主機、`localhost`、單節主機名與 `.local`、`.internal` 結尾；DNS 解析後的位址不得是私有、迴環或鏈路本地位址。
- 轉址手動跟隨，最多 5 次，每一跳重新檢查。
- 網頁：逾時 10 秒，內容型別須為 HTML，最多讀 2 MB。
- 遇到 401、403、429、驗證挑戰頁，一律停止並記為「網站不允許自動擷取」。**不得**用任何方式繞過。
- 使用固定且誠實的 User-Agent，不送 cookie。
- 存進資料庫的只有解析出的純文字；畫面以一般方式跳脫輸出。

### B7. 畫面與互動

**主頁**

- 上方依序：貼網址輸入框（最顯眼）、手動新增、搜尋、狀態篩選、排序、圖庫／列表切換、選單（回收桶、改暱稱、登出）。
- 狀態篩選：全部（不含不考慮，預設）、未討論、待確認、確定考慮、不考慮。
- 排序：最近新增（預設）、月租金低到高／高到低、坪數大到小／小到大。空值排最後。
- 搜尋在瀏覽器端進行，比對名稱、地區、地址、物件描述、目前結論、樓層與用途。
- 篩選、搜尋、排序、檢視方式在開關面板與資料更新後都要維持不變。

**圖庫**

- 相簿風格：緊密格線、小間距。手機兩欄，桌面自動填滿。卡片比例 4:3。
- 每張卡片：封面、名稱、月租金、坪數、狀態標籤；有填規劃時加一個小標記。沒有照片的物件顯示名稱色塊。

**列表**

- 欄位：封面縮圖、名稱、地區、月租金、坪數、狀態。手機上改為緊湊的單列卡片。點任一列開啟同一個詳細面板。

**詳細面板**

- 桌面：右側固定 50% 寬；左側圖庫縮到另一半、仍可捲動與點選，被選中的卡片要標示出來。手機：全螢幕。
- 開啟面板不向伺服器要資料（主頁一次載入全部物件、照片清單與討論紀錄），所以是即時的。
- 內容由上到下，依「看照片、討論」的優先順序：
  1. 標題列：上一間／下一間、名稱、關閉。
  2. 照片輪播（可滑動）；點照片進全螢幕大圖，大圖可左右切換。
  3. 狀態（四個按鈕，一鍵切換）與規劃。
  4. 重點資訊：月租金、坪數、地區；「原始刊登」連結（開新分頁）；「Google Maps」連結（以地址組成地圖搜尋網址，不接地圖 API；沒有地址就不顯示）。
  5. 目前結論：可直接編輯，顯示最後更新者與時間。
  6. 討論紀錄：時間軸與輸入框。
  7. 詳細資料：地址、押金／其他費用、樓層與用途、物件描述；編輯、上傳照片、管理照片、再試一次匯入。
  8. 刪除（放在次要位置，需確認）。
- 上一間／下一間依目前的篩選與排序結果切換。

**網址狀態與返回鍵**

- 面板開著時網址帶 `?item=<物件 id>`；大圖開著時再帶 `&photo=<第幾張>`。這個網址就是物件的直達連結。
- 開啟面板、開啟大圖各新增一筆瀏覽紀錄；上一間／下一間、切換照片不新增瀏覽紀錄。
- 返回鍵、X、Esc 行為一致：先關大圖，再關面板。關閉後圖庫的捲動位置不變。
- 從直達連結進來時沒有站內瀏覽紀錄，關閉面板改為直接移除網址參數並留在倉庫。

**資料更新與同時編輯**

- 不做即時同步。每次寫入後更新畫面；分頁重新回到前景時自動重新取得資料（至少間隔 15 秒）。自動更新不得清掉正在輸入、尚未送出的文字。
- 狀態：最後寫入者為準。狀態真的有變時，同一筆交易內寫入一則狀態異動。
- 目前結論：送出時帶上自己看到的更新時間；若期間已被別人改過，拒絕寫入、保留自己的草稿，並顯示對方的版本讓股東決定。
- 其他欄位：只送出有改動的欄位，最後寫入者為準。
- 留言：可新增；任何股東可刪除留言（需確認）。狀態異動不可刪除。

**回收桶**

- 選單內的回收桶列出已刪除物件（封面、名稱、誰在何時刪除），可還原。還原後照片、目前結論、討論紀錄完整。
- 不提供永久刪除。

### B8. 明確不做

個人帳號、角色權限、邀請連結、即時同步、通知、排程、AI 分析、法規查核、物件比較、地圖 API、樓層資料表、規劃篩選、合併重複刊登、其他房仲站專用解析、第二把去重鍵、匯入後自動更新刊登內容、永久刪除、管理後台、資料匯出。

## D. 開發階段與先後順序

每一步都要能獨立驗證再往下走。每個階段結束時的關卡相同：AC31 通過、冒煙腳本通過、該階段的驗收標準逐條確認。

2. 本機資料庫與 schema 腳本可重複執行。
3. `lib/storage.ts` 與本機磁碟模式可用。

### D2. 階段一：可上線可用

依序完成：

1. 進出控制：登入頁、session、`proxy.ts`、`verifySession()`、登出、改暱稱。（AC1–AC3、AC5）
2. 物件基本流程：手動新增、圖庫、詳細面板、網址狀態與返回鍵、上一間／下一間、編輯欄位、Google Maps 與原始刊登連結。（AC13、AC17、AC18、AC20–AC22、AC29）
3. 討論：狀態切換與狀態異動、目前結論（含同時編輯提示）、留言。（AC23–AC25）
4. 照片：瀏覽器壓縮、上傳、封面、刪除、輪播、全螢幕大圖、縮圖。（AC14、AC15、AC19、AC30）
5. 貼網址新增：取網址、去重鍵（含全部 591 規則與短連結）、建立物件、安全抓取、通用解析、再試一次。（AC7、AC9–AC12、AC16、AC33）
6. 刪除與回收桶。（AC28）
7. 分頁回到前景自動更新、空白狀態、錯誤訊息、手機版檢查。（AC4）
8. 冒煙腳本與階段一驗收；取得部署授權後依 D4 上線。（AC6）
