## A. 設計結論

### A1. 目的與使用情境

**要解決的問題**

Potions Magic Bar 的股東正在找第二間店的店面。物件散落在 591、各家房仲網站、仲介的 LINE 訊息與路邊的招租紅單，股東之間靠聊天室傳連結討論，過幾天就找不到哪一間談到哪裡、誰說了什麼、為什麼排除。

**解法**

一個只有股東能進的私人網站「Potions 二店選址倉庫」：把所有候選物件收在同一處，以照片為主瀏覽，每個物件有狀態、一段目前結論、一條討論紀錄。它是共用的候選物件倉庫，不是房仲平台、CRM 或法規審查系統。

**核心流程**

1. 股東在 591 或其他網站看到物件，複製網址。
2. 貼進倉庫，網站立刻建立物件，並盡量自動帶入照片與基本資料。
3. 帶不進來的部分由股東手動補填、上傳照片或截圖。
4. 股東們看照片、開原始刊登、討論，改狀態、寫下目前結論。
5. 日後用狀態篩選、搜尋、排序快速回顧。

**使用情境**

1. 身為股東，我想貼上 591 或其他網站的刊登網址就建立物件，以便不必手動抄資料。
2. 身為股東，我想在網站擋機器或抓取失敗時仍然建立物件並讓我補填，以便任何來源的物件都進得了倉庫。
3. 身為股東，我想手動新增沒有網址的物件（仲介私訊、路邊招租），以便沒上網刊登的店面也能討論。
4. 身為股東，我想在重複貼同一則刊登時被帶到既有物件，以便討論不會分散成兩處。
5. 身為股東，我想上傳自己拍的照片或截圖並指定封面，以便看屋當天的照片也留在物件裡。
6. 身為股東，我想在圖庫用照片快速掃過所有候選物件，以便一眼分辨哪幾間值得細看。
7. 身為股東，我想點物件就看到大圖與詳細資訊而不離開圖庫，以便看完一間馬上回到原本的位置。
8. 身為股東，我想用上一間／下一間連續看，以便開會時一間一間過。
9. 身為股東，我想一鍵把物件標成四種狀態之一，以便大家知道每一間目前的處置。
10. 身為股東，我想寫下並隨時修改這間物件的目前結論，以便不必翻完整串討論才知道現況。
11. 身為股東，我想留言並看到誰在何時說了什麼、誰改了狀態，以便追溯決定的來龍去脈。
12. 身為股東，我想用狀態篩選、搜尋、排序找物件，以便物件變多之後仍找得到。
13. 身為股東，我想切換成列表，以便並排比較月租金與坪數。
14. 身為股東，我想從物件直接開啟原始刊登與 Google Maps，以便查看完整刊登與位置。
15. 身為股東，我想把某個物件的直達連結貼到 LINE 群組，以便其他股東點了就看到同一間。
16. 身為股東，我想在自己的手機或電腦看到和其他股東完全相同的資料，以便大家討論的是同一份。
17. 身為股東，我想在誤刪物件後從回收桶還原，以便手滑不會造成損失。
18. 身為股東，我只想用一組共享密碼和自己取的暱稱進入，以便不必註冊帳號。
19. 身為股東，我想在手機上順利完成以上所有事，以便看屋途中就能使用。
20. 身為選址負責人，我想讓展演只是可選的規劃標記，以便不適合展演的物件也能正常評估。

**三條不可違反的原則**

1. **二店選址是唯一主軸。** 展演只是部分物件可能的複合規劃。任何流程都不得要求填寫展演相關資訊。
2. **看照片與共同討論優先。** 圖庫、列表、篩選、詳細面板的每個取捨，都以「照片出現得快、討論寫得順」為先，其他資訊退到次要位置。
3. **保持簡單、最快交付。** 本規格書沒寫的功能就不做。

### A2. 已定案的決議

| 主題 | 決議 |
|---|---|
| 形式 | 客製化網站，不用 Notion。目標是最快做出可分享的網站，不承諾完成時間。 |
| 資料與照片 | Neon Postgres ＋ Vercel Blob。不用 Supabase，因為它的免費專案閒置七天會暫停、要人工喚醒。見 ADR-0002。 |
| 照片公開性 | 照片放公開的 Blob store，靠不可猜的網址保護。見 ADR-0003。 |
| 進出 | 一組共享密碼＋自填暱稱，沒有個人帳號，沒有免密碼邀請連結。見 ADR-0001。 |
| 登入保存 | 登入狀態保存 90 天；更換共享密碼後所有裝置自動失效。 |
| 新增物件 | 貼網址（匯入）與手動新增兩條路。匯入失敗也一定建立物件，再由股東補填。 |
| 匯入範圍 | 兩層：591 店面出租頁的專用解析，其他網址一律只讀標題、描述、封面。不做其他房仲站的專用解析。 |
| 匯入次數 | 只在建立物件時匯入一次。不做重新抓取。 |
| 去重 | 同一來源網址只能有一個物件；比對前先正規化網址、忽略追蹤參數。重複時直接開啟既有物件。 |
| 照片處理 | 上傳前在瀏覽器壓縮；匯入時把刊登照片複製進自己的儲存，不外連。 |
| 欄位 | 只照租賃設計（月租金）。出售刊登可以貼，但不自動帶入價格。 |
| 來源平台 | 由來源網址判斷，不設欄位；「原始刊登」連結上顯示網站主機名。 |
| 狀態 | 固定四種：未討論、待確認、不考慮、確定考慮。任何股東可直接改。 |
| 目前結論 | 每個物件一段可隨時編輯的文字，記錄當下的共識與重要備註。 |
| 討論紀錄 | 依時間排列的留言（暱稱＋時間），狀態異動自動記入同一條時間軸。 |
| 刪除 | 物件軟刪除進回收桶，可還原。單張照片的刪除是永久的。 |
| 詳細面板 | 桌面右側 50%、手機全螢幕；照片輪播、全螢幕大圖、上一間／下一間；X、Esc、瀏覽器返回鍵都能關。 |
| 直達連結 | 每個物件有可分享的直達連結；未登入者仍須先輸入共享密碼。 |
| 檢視 | 圖庫（預設）與列表，共用篩選、搜尋、排序；預設不顯示「不考慮」。 |
| 樓層 | 一個多行文字欄「樓層與用途」，不建樓層表。 |
| 規劃 | 單選：未定（預設）／純二店／二店＋展演。只顯示，不做篩選，不是必填。 |
| 重複刊登 | 不合併。一個物件對應一則刊登，發現重複由股東自行刪除。 |
| 同步 | 不做即時同步；切回分頁時自動重新取得資料。 |
| 交付 | 分兩階段；階段一就包含貼網址新增。最終驗收項目不因分階段而減少。 |

### A3. 查證後需要大哥知悉的四件事

這四件不是新問卷，規格已各自採用下述預設。只有第 1 點需要大哥本人動手（付費升級）；其餘若要改，授權時說一聲即可。

1. **Vercel Hobby 不能明確算合規，規格預設採 Vercel Pro 單一席位。**
   - 服務條款第 4 條（2026-10-19 版）原文：「You shall only use the Services under a Hobby plan for your personal or non-commercial use.」
   - Vercel 目前已不再公布「商業用途」的定義，對「營利事業的內部工具」也沒有官方答覆。本工具是營利事業的內部商業工具，屬灰色地帶且偏向不合規。同一條款允許 Vercel 不經通知停用 Hobby 專案。
   - Pro：US$20／月（未稅），內含 1 個部署席位與 US$20 用量額度。股東只是開網址，不需要 Vercel 帳號也不佔席位。本專案規模的用量預期落在內含額度內。
   - 目前帳號是哪個方案，工具讀不到，推測是 Hobby；請大哥在 Vercel 後台 Settings › Billing 確認。
   - 開發與自測可在現有方案上進行；**放入真實物件、交給股東使用之前**升級。升級是購買行為，只能由大哥本人操作。
   - 不想付費的替代方案（Netlify 免費版、Cloudflare）都要改寫儲存層，多出半天到兩天工程，與最快交付相違，故不採用。
2. **GitHub repo 目前是公開的。** 規格、名詞表任何人都看得到。規格規定程式庫內不得放密碼與真實物件資料，所以公開不會洩漏資料；但這是公司內部的展店規劃，建議改為私人（GitHub › Settings › General › Danger Zone，只有大哥能改）。改為私人後，由開發代理身分提交的版本有可能被 Vercel 擋下不自動部署；改完要先試一次部署，被擋時改由 Vercel 後台或部署工具觸發。
3. **591 頁尾有禁止自動下載的聲明。** 原文：「亦不得使用網路爬蟲或其他自動下載程式或任何其他類似或具相同功能的手動程序來連續自動搜索、獲得、使用、下載，如有違反……本公司將收取一個刊登物件內容，三千元計算之費用」。591 的 robots.txt 本身不禁止抓取。
   - 規格預設維持大哥的決議（匯入時複製照片），並把行為限制在最窄：只在股東貼上網址時抓那一頁一次，不排程、不重抓、不抓列表頁、不繞過任何防護。
   - 這是否可接受屬於法律與商業判斷，無法由開發方代為認定。較保守的做法是「591 只存連結與文字、照片由股東截圖上傳」，改動很小。
4. **591 以外的網站大多抓不到。** 實測十家房仲站：樂屋、永慶、台灣房屋擋機器，太平洋是前端渲染抓不到內容，信義與 21 世紀可抓到標題，其餘四家當天沒測到有效刊登。所以「貼網址→建立物件→手動補填與上傳照片」是 591 以外的主要流程，必須順手。

### A4. 第一版範圍總覽

第一版（MVP）等於階段一加階段二，兩個階段的項目**全部必做**，驗收標準是 C 部分的 AC1–AC34。分階段只是為了先有能用的網站。

| 類別 | 內容 |
|---|---|
| 第一版必做・階段一（先上線） | 共享密碼＋暱稱登入；貼網址新增（一定建立物件、通用匯入、去重）；手動新增；人工補填；照片上傳、封面、刪除；圖庫與狀態篩選；詳細面板（輪播、大圖、上一間／下一間、返回鍵）；四種狀態與狀態異動；目前結論；留言；原始刊登與 Google Maps 連結；直達連結；回收桶與還原；切回分頁自動更新。 |

| 未來可延伸（第一版不做） | 見 B8 第一組，例如手動重新匯入、修改留言、其他房仲站專用解析、資料匯出。 |
| 不在本工具範圍 | 見 B8 第二組，例如 AI 分析、法規查核、排程、管理後台。 |

## B. 技術架構

### B1. 技術選型

| 項目 | 選擇 |
|---|---|
| 框架 | Next.js（App Router）＋ TypeScript。以動工當下 `create-next-app` 的最新穩定版為準（查證日為 16.4.6）。 |
| 樣式 | Tailwind CSS（查證日為 v4，CSS-first 設定）。不引入 UI 元件庫。 |
| 主機 | Vercel，Functions 區域 `sin1`（新加坡），與資料庫同區。 |
| 資料庫 | Neon Postgres，經 Vercel Marketplace 安裝，Free 方案，新加坡區域。一個資料庫。 |
| 資料存取 | `pg` 連線池＋參數化 SQL。不用 ORM，不用 migration 框架。 |
| 照片 | Vercel Blob，一個公開 store，區域 `sin1`。 |
| 測試 | Vitest，只測純函式；另有一支瀏覽器冒煙腳本。見 B9。 |

該版本 Next.js 與舊版差異大（查證日：攔截檔是 `proxy.ts` 而非 `middleware.ts`；`cookies()` 等是非同步；Server Action 是公開端點、本文上限 1 MB）。實作前先讀 `node_modules/next/dist/docs/` 的對應文件，不憑記憶寫。

### B2. 部署方案

- 正式站：Vercel Pro、一個席位（理由見 A3 第 1 點）。Deployment Protection 維持預設的 Standard Protection：正式網址公開、由本站自己的共享密碼把關；預覽網址需要 Vercel 登入，只有大哥與開發代理看得到。
- 正式分支是 `main`。開發在該次工作階段指定的開發分支上進行（撰寫時為 `claude/optimistic-gates-9v9rmn`），通過階段驗收的版本才推進 `main`。`main` 必須在建立 Vercel 專案**之前**就存在，否則 Vercel 會把開發分支當成正式分支。
- 一個 Neon 資料庫，連到 Production 與 Preview（後台預設值），不啟用 Preview Branching。預覽部署因此讀寫同一份資料。開發代理不在任何已部署的站上建立資料。
- 全站回應帶 `X-Robots-Tag: noindex, nofollow`，並設定頁面 metadata 的 robots 為不索引。
- 環境變數只有一個需要人工設定：`SITE_PASSWORD`。資料庫與 Blob 的變數由 Vercel 在連接時自動注入。
- 程式庫內不得出現密碼、`.env` 檔、真實物件資料。提供只列變數名稱的 `.env.example`。

上線步驟見 D4。

### B3. 資料模型與物件欄位

三張表。程式裡「物件」的代號一律是 `item`（資料表 `items`、外鍵 `item_id`、網址參數 `item`）；`listing` 這個字保留給「刊登」，避免混用。畫面文字一律用名詞表的中文。

**`items`（物件）**

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | uuid，主鍵 | |
| `name` | text，必填 | 名稱，最長 120 字。唯一的必填欄位 |
| `source_url` | text，可空 | 來源網址。手動新增的物件沒有；建立後不可修改 |
| `url_key` | text，可空 | 去重鍵，見 B6。非空值唯一，回收桶內的物件也算 |
| `region` | text | 地區，例：台北市信義區 |
| `address` | text | 地址 |
| `rent` | integer，可空 | 月租金（新台幣）。未知或面議時留空 |
| `area` | numeric(8,2)，可空 | 坪數 |
| `fees` | text | 押金／其他費用（文字，頂讓金也寫這裡） |
| `floors` | text | 樓層與用途（多行文字，例：1F 50 坪店舖；B1 44 坪防空避難室） |
| `description` | text | 物件描述（取自刊登的原始說明） |
| `plan` | text，預設 `undecided` | 規劃：`undecided` 未定／`pure` 純二店／`with_show` 二店＋展演 |
| `status` | text，預設 `new` | 狀態：`new` 未討論／`pending` 待確認／`rejected` 不考慮／`shortlisted` 確定考慮 |
| `conclusion` | text | 目前結論 |
| `conclusion_by`、`conclusion_at` | text、timestamptz，可空 | 目前結論最後由誰、何時更新 |
| `created_by`、`created_at`、`updated_at` | | 建立者暱稱與時間 |
| `deleted_at`、`deleted_by` | 可空 | 非空代表在回收桶 |

| 欄位 | 說明 |

| `created_by`、`created_at` | |

| `body` | 留言內容；狀態異動時為空 |
| `from_status`、`to_status` | 只有狀態異動使用 |
| `nickname`、`created_at` | |

規則：

- Schema 寫在單一檔案 `db/schema.sql`，可重複執行、只增不減（`CREATE TABLE IF NOT EXISTS`、`ADD COLUMN IF NOT EXISTS`、`CREATE INDEX IF NOT EXISTS`）。由 `scripts/db-setup.mjs` 在建置指令中套用：`node scripts/db-setup.mjs && next build`。在 Vercel 上若沒有資料庫連線字串，腳本必須失敗；在本機沒有時略過並警告。
- 執行期用 `DATABASE_URL`（連線池），schema 腳本用 `DATABASE_URL_UNPOOLED`。SQL 寫成 PostgreSQL 16 相容。
- 不加任何定時連資料庫的保活或排程。

### B4. 共享、進出控制與權限

**共享與權限**

- 所有股東共用同一份資料。任何寫入都存進資料庫，其他股東重新整理或切回分頁就看得到。
- 所有股東權限相同：都能新增、編輯、改狀態、留言、刪除物件、從回收桶還原。沒有管理員，沒有審核程序。
- 暱稱不經驗證，只用來標示留言與狀態異動是誰做的。
- 資料庫與照片的寫入只經過伺服器，瀏覽器拿不到任何資料庫或儲存的憑證。

**進出控制**

- 環境變數 `SITE_PASSWORD`。未設定或少於 8 個字元時，一律拒絕登入（封閉式失敗）。建議 12 個字元以上。
- 登入頁只有兩個欄位：共享密碼、暱稱（1–20 字）。共享密碼在伺服器驗證。
- 登入成功後設定兩個 cookie，都是 `httpOnly`、`secure`、`sameSite=lax`、有效 90 天：
  - `ark_session`：以 `SITE_PASSWORD` 為金鑰、對固定字串做 HMAC-SHA256 的結果。伺服器用定時安全比較驗證。換密碼並重新部署後，舊 cookie 自動失效，不需要第二個密鑰。
  - `ark_nick`：暱稱。中文暱稱要先編碼再寫入 cookie。
- 驗證做兩層：
  - `proxy.ts`：沒有有效 cookie 的頁面請求，導向 `/login?next=<原路徑與查詢字串>`。`next` 只接受以單一 `/` 開頭的站內路徑。
  - `verifySession()`：每一個 Server Action、每一個 Route Handler、每一個讀資料的伺服器元件，第一步都要呼叫。失敗回 401 或導向登入。
- 未登入時的任何回應，都不得包含物件資料或照片網址。
- 密碼錯誤時回一般性錯誤訊息並延遲約半秒。不做鎖定機制。
- 可登出。要改暱稱就登出後重新登入；舊的留言保留當時的暱稱。

### B5. 照片

**儲存**

- 一個公開 Blob store。每次寫入都用伺服器產生的路徑，並加上隨機字尾，不使用原始檔名。路徑以環境區分：正式環境 `prod/…`，其餘 `dev/…`。
- 所有 Blob 存取集中在 `lib/storage.ts`（只匯出存、刪兩種操作），其他檔案不得直接引用 `@vercel/blob`。
- 判斷用哪種儲存：環境變數 `BLOB_STORE_ID` 或 `BLOB_READ_WRITE_TOKEN` 任一存在就用 Blob。兩者皆無且在 Vercel 上（`VERCEL` 已設定）時直接報錯，不得退回本機磁碟。兩者皆無且不在 Vercel 上時用本機磁碟，由一支只在開發環境存在的路由提供照片。這讓開發機不需要任何雲端憑證。
- 已知取捨：拿到某張照片網址的人不需共享密碼就能看到那一張；換密碼不會讓照片網址失效，刪除照片才會。上傳介面提示「請勿上傳合約、證件等機密文件」。

**股東上傳**

- 瀏覽器先壓縮：長邊不超過 1600px 的 JPEG。壓縮後超過 1 MB 就降低品質重壓，直到不超過 1 MB。壓縮後方向必須正確（手機直拍的照片不可橫躺）。瀏覽器無法解碼的格式顯示錯誤，不送出原檔。
- 一次請求只傳一張（Vercel 單次請求上限 4.5 MB），用 Route Handler 接收，不用 Server Action。前端同時最多傳 3 張，逐張顯示進度，失敗可單張重試。
- 伺服器檢查：已登入、物件存在且不在回收桶、大小不超過 4 MB、檔頭確實是 JPEG／PNG／WebP、該物件照片未達上限。
- 每個物件照片合計最多 50 張。

**匯入照片**

- 匯入時由伺服器下載刊登照片並存入儲存，最多 20 張，同時最多 4 張，每張逾時 10 秒，整批最多 45 秒，時間到就停、已完成的保留。任何一張失敗都跳過，不影響物件與其他照片。
- 只接受 JPEG／PNG／WebP／GIF／AVIF（同時檢查 Content-Type 與檔頭），單張上限 8 MB。照原樣儲存，不重新編碼。
- 通用匯入取得的 `og:image`，若它的網址已是同網站另一個物件的 `source_photo_url`，視為網站預設圖，不匯入。
- 匯入完成後，畫面上的照片一律來自自己的儲存，不直接連到刊登網站。

**顯示**

- 圖庫與列表的封面用縮圖（`next/image`）。面板輪播與全螢幕大圖直接用原圖。
- `images.remotePatterns` 設為 `https://*.public.blob.vercel-storage.com/**`。用萬用字元是因為 store 的主機名要到上線步驟才產生，不想為此多一次改設定的提交。本機磁碟模式下縮圖可不最佳化。縮圖額度出問題時，設定 `images.unoptimized` 是一行退路。
- 所有照片 `loading="lazy"`，用已知寬高預留版位。
- 封面是 `sort_order` 最小的照片；「設為封面」就是把它排到最前。
- 刪除單張照片需確認，確認後永久刪除（同時刪除儲存中的檔案）。物件進回收桶時不刪任何照片。

### B6. 網址匯入、人工補填與去重

**流程**

1. 股東在輸入框貼上內容（可夾雜文字）。伺服器取出第一個網址。沒有網址時不建立物件，提示改用手動新增。
2. 計算去重鍵 `url_key`（規則見下）。591 的短分享連結要先跟隨轉址才知道物件編號。
3. 以 `url_key` 查既有物件（含回收桶）：
   - 已存在且未刪除：不新增，直接開啟該物件並提示「這個物件已經在倉庫裡」。
   - 在回收桶：詢問「此物件在回收桶，要還原嗎？」。選否就什麼都不建立。
   - 不存在：立即建立物件。建立時的名稱取貼上內容中網址以外的文字（去掉結尾的「詳情：」與標點，截到 120 字）；沒有文字就用「來自 <網站主機名> 的物件」。兩人同時貼同一網址時，靠唯一索引只留下一個。
4. 畫面馬上出現新物件並開啟面板，同時在背景呼叫匯入端點一次。
5. 匯入端點抓取該頁一次、解析、寫入空白欄位，再複製照片，回傳結果摘要。名稱的規則：匯入取得標題，且物件名稱仍是建立時的值（股東還沒改過），才以標題取代。
6. 面板顯示結果：成功時列出帶入了什麼；失敗或部分成功時顯示原因，並直接進入編輯。原因只有兩種說法：「此網站不允許自動擷取，請手動補填」與「刊登不存在或無法讀取，請手動補填」。

匯入只在建立物件時執行這一次。之後的補充全靠股東手動編輯與上傳。

**人工補填**

- 任何物件都能隨時編輯。可編輯的欄位：名稱、地區、地址、月租金、坪數、押金／其他費用、樓層與用途、物件描述、規劃。
- 可上傳照片或截圖、指定封面、刪除單張照片（見 B5）。
- 匯入失敗的物件，建立後面板直接停在編輯狀態，來源網址已保留，股東補上其餘內容即可。
- 手動新增只需要填名稱；其餘欄位與照片之後再補。

**去重鍵規則**

- 取網址：從貼上文字找第一個 `http(s)://` 開頭的片段，遇到空白或全形標點即結束，去掉結尾的半形標點。
- 591：鍵為 `591:<rent|sale|ding>:<物件編號>`，忽略主機名與所有查詢參數。完整的網址形狀與正規表示式見附錄第 1 節，至少涵蓋：
  - `business.591.com.tw/rent/<id>`、`business.591.com.tw/sale/<id>`
  - `rent.591.com.tw/<id>`、`rent-detail-<id>.html`（rent、www、m 三種主機）
  - `m.591.com.tw/v2/rent/<id>`、`m.591.com.tw/v2/business/rent/<id>`（sale 同理）
  - `store.591.com.tw/ding-detail-<id>.html`（頂讓，獨立的編號序列）
  - 路徑以 `/mobile-detail.html` 結尾且帶 `houseId=R|S|D<id>`
  - 短分享連結（591 主機、路徑為 1–8 個英數字、帶 `salt` 參數）：手動跟隨轉址，最多 5 次、總時間 5 秒，每一跳都必須是 https 且主機為 `591.com.tw` 或其子網域，對每個轉址目標套用上述規則。
- 591 的 `source_url` 存重組後的標準網址（三種類型的樣板見附錄第 1 節），不保存 `s`、`salt` 等分享參數。短連結解析不出編號時退回通用規則，`source_url` 保留原短連結並去掉 `s` 參數。
- 其他網站（通用規則）：
  1. 只接受 `http`、`https`，且網址不得帶帳號密碼；否則不產生鍵（物件仍然建立）。
  2. 鍵不含協定；主機名轉小寫並去掉開頭的 `www.`；省略預設連接埠。**不**去掉 `m.` 之類的前綴。
  3. 路徑保留大小寫，去掉結尾的 `/`。
  4. 查詢參數：刪除追蹤參數後，其餘**全部保留**並依名稱排序，參數值保留大小寫。許多房仲站把物件編號放在查詢參數（樂屋 `ehid`、住商 `sn`、太平洋 `saleID`），所以不在刪除名單上的參數一律不能動。
  5. 刪除名單（不分大小寫）：`utm_` 開頭的全部，以及 `fbclid`、`gclid`、`gbraid`、`wbraid`、`dclid`、`msclkid`、`yclid`、`twclid`、`ttclid`、`igshid`、`igsh`、`mibextid`、`mc_cid`、`mc_eid`、`_ga`、`_gl`、`srsltid`、`openExternalBrowser`、`openInAppBrowser`。
  6. 去掉 `#` 之後的片段，除非以 `#/` 或 `#!/` 開頭。
  7. `source_url` 存去掉追蹤參數後的網址。
- 不做第二把鍵（不拿 `rel=canonical` 或 `og:url` 再比一次）、不做其他房仲站的專用規則。已知後果：同一刊登若有兩種完全不同的網址形狀，可能建出兩個物件，由股東自行刪除其一。

**解析**

- 最終狀態碼不是 200 就不解析。
- 通用（階段一）：名稱取 `og:title`，沒有就取 `<title>`；物件描述取 `og:description`，沒有就取 meta description；照片取 `og:image` 一張。
- 591 進階（階段二），**只**適用店面出租頁 `business.591.com.tw/rent/<id>`。欄位來源與正規表示式見附錄第 2、3 節：
  - 優先讀 JSON-LD，再讀 meta，不解析頁面內嵌的 `__NUXT__` 資料。
  - 名稱、月租金、地址、地區、樓層取自 JSON-LD；坪數取自描述句；押金取自頁面文字，原文存入「押金／其他費用」。
  - 照片取 JSON-LD 的 `image` 陣列，只留 `/house/年/月/日/` 路徑的圖，以去掉主機名與 `!` 尺寸字尾後的路徑去重，照頁面給的網址原樣下載。
- 591 的出售頁、住宅頁、頂讓頁一律走通用解析，不帶入月租金；頂讓頁的照片由股東手動上傳。
- 每一條解析規則都要「抓不到就留空」，不得因為某欄解析失敗而讓整次匯入失敗。

**抓取安全與禮貌**

- 只有已登入的股東能觸發；一次貼上只抓一頁，不自動重試、不排程、不抓列表頁。
- 只接受 `http`、`https`；拒絕 IP 位址形式的主機、`localhost`、單節主機名與 `.local`、`.internal` 結尾；DNS 解析後的位址不得是私有、迴環或鏈路本地位址。
- 轉址手動跟隨，最多 5 次，每一跳重新檢查。
- 網頁：逾時 10 秒，內容型別須為 HTML，最多讀 2 MB。
- 遇到 401、403、429、202 或帶有驗證挑戰標頭的回應，一律停止並記為「此網站不允許自動擷取」；其他非 200 記為「刊登不存在或無法讀取」。**不得**用任何方式繞過。
- 使用固定且誠實的 User-Agent，不送 cookie。
- 存進資料庫的只有解析出的純文字；畫面以一般方式跳脫輸出。
- 抓取函式做成可注入的，測試時換成回傳手寫樣本的假抓取。正式程式不得有任何放行本機位址的開關。

### B7. 畫面與互動

設計語言參考 iOS 相簿：照片為主、資訊精簡。全站繁體中文，網站名稱顯示為「Potions 二店選址倉庫」。手機與桌面都要好用。時間一律以台北時間顯示。

**主頁**

- 上方依序：貼網址輸入框（最顯眼）、手動新增、搜尋、狀態篩選、排序、圖庫／列表切換、選單（回收桶、登出）。
- 狀態篩選：全部（不含不考慮，預設）、未討論、待確認、確定考慮、不考慮。
- 排序：最近新增（預設）、月租金低到高／高到低、坪數大到小／小到大。空值排最後。
- 搜尋在瀏覽器端進行，比對名稱、地區、地址、物件描述、目前結論、樓層與用途。
- 篩選、搜尋、排序、檢視方式由圖庫與列表共用，在開關面板與資料更新後都要維持不變。

**圖庫（預設檢視）**

- 相簿風格：緊密格線、小間距。手機兩欄，桌面自動填滿。卡片比例 4:3。
- 每張卡片：封面、名稱、月租金、坪數、狀態。規劃是「純二店」或「二店＋展演」時加一個小標記，「未定」不顯示。沒有照片的物件顯示名稱色塊。

**列表**

- 欄位：封面縮圖、名稱、地區、月租金、坪數、狀態。手機上改為緊湊的單列卡片。點任一列開啟同一個詳細面板。

**詳細面板**

- 桌面：右側固定 50% 寬；左側圖庫縮到另一半、仍可捲動與點選，被選中的卡片要標示出來。手機：全螢幕。
- 開啟面板不向伺服器要資料（主頁一次載入全部物件、照片清單與討論紀錄），所以是即時的。
- 內容由上到下，依「看照片、討論」的優先順序：
  1. 標題列：上一間／下一間、名稱、關閉。
  2. 照片輪播（可滑動）；點照片進全螢幕大圖，大圖可左右切換。
  3. 狀態（四個按鈕，一鍵切換）與規劃。
  4. 重點資訊：月租金、坪數、地區；「原始刊登（<網站主機名>）」連結，開新分頁；「Google Maps」連結，以地址組成地圖搜尋網址，不接地圖 API，沒有地址就不顯示。
  5. 目前結論。
  6. 討論紀錄。
  7. 詳細資料：地址、押金／其他費用、樓層與用途、物件描述；編輯、上傳照片、管理照片。
  8. 刪除（放在次要位置，需確認）。
- 面板顯示的是網址上指定的物件，不受篩選與搜尋影響。物件因為改了狀態、資料更新或直達連結而不符合目前的篩選時，面板保持開啟，該物件也暫時留在圖庫與上一間／下一間的順序裡，直到面板關閉或切到別的物件。
- 上一間／下一間依目前的篩選與排序結果切換。到第一間或最後一間時按鈕停用，不循環。
- 網址指向回收桶內或不存在的物件時，顯示「找不到這個物件」。

**四種狀態**

| 狀態 | 意思 |
|---|---|
| 未討論 | 還沒有股東討論過。新物件一律是這個狀態。 |
| 待確認 | 討論過，但還有事項要查證才能決定。 |
| 不考慮 | 已排除。被別人租走的物件也改成這個狀態，再留言說明。物件仍在倉庫裡，只是預設不顯示。 |
| 確定考慮 | 列入認真評估的名單。 |

- 任何股東都能直接切換，沒有審核程序，可以在四種之間任意來回。
- 狀態真的有變時，同一筆交易內寫入一則狀態異動，顯示為「<暱稱> 將狀態從 A 改為 B」。
- 狀態與規劃是兩回事：狀態是討論進度，規劃只是經營型態的標記。

**目前結論與討論紀錄**

這是兩個分開的功能。

- **目前結論**（股東的重要備註）：每個物件一段文字，可在面板上直接編輯，隨時改寫。顯示最後更新者與時間。以最後寫入者為準。
- **討論紀錄**：依時間排列的時間軸，由兩種紀錄組成。輸入框在最上方，紀錄由新到舊排列。
  - 留言：股東寫下的發言，顯示暱稱與時間。只能新增，不能修改或刪除。
  - 狀態異動：改狀態時自動產生，不能刪除。
- 尚未送出的留言與目前結論草稿依物件留在瀏覽器記憶體：自動更新、關閉面板、切換物件都不會清掉，同一次瀏覽內重開仍在；重新整理頁面後不保留。

**網址狀態與返回鍵**

- 面板開著時網址帶 `?item=<物件 id>`；大圖開著時再帶 `&photo=<第幾張>`。這個網址就是物件的直達連結。
- 開啟面板、開啟大圖各新增一筆瀏覽紀錄。上一間／下一間、面板開著時點另一張卡片、切換照片，都不新增瀏覽紀錄。
- 返回鍵、X、Esc 行為一致：先關大圖，再關面板。關閉後不會跳回頂端：手機上圖庫停在原本的位置，桌面上最後檢視的那張卡片仍在畫面內。
- 從直達連結進來時沒有站內瀏覽紀錄，關閉面板改為直接移除網址參數並留在倉庫。

**資料更新**

- 不做即時同步。每次寫入後更新畫面；分頁重新回到前景時自動重新取得資料（至少間隔 15 秒）。
- 所有欄位都以最後寫入者為準。編輯時只送出有改動的欄位。

**回收桶**

- 選單內的回收桶列出已刪除物件（封面、名稱、誰在何時刪除），可還原。還原後照片、目前結論、討論紀錄完整。
- 不提供永久刪除。

### B8. 第一版不做的事

**第一組：未來可延伸。** 第一版不做，日後真的需要時可以加，都不影響現有資料。

- 手動重新匯入（「再抓一次」）、匯入後自動更新刊登內容
- 修改來源網址、為手動新增的物件補上來源網址
- 修改或刪除留言
- 目前結論的同時編輯偵測
- 其他房仲站的專用解析、第二把去重鍵、合併重複刊登
- 規劃篩選
- 改暱稱功能（目前以重新登入代替）
- 物件永久刪除
- 資料匯出
- 即時同步、通知
- 個人帳號、角色權限
- 物件比較、地圖 API、樓層資料表

**第二組：不在本工具範圍。** 已決議不做。

- AI 分析與評分
- 自動法規或適法性查核
- 排程任務與定時爬蟲
- 管理後台
- 免密碼邀請連結

### B9. 測試方式

- 好的測試只驗外部行為，不驗內部實作。
- **單元測試**只針對純函式：去重鍵、從貼上文字取網址、通用解析、591 解析、session 簽章、照片檔頭檢查、抓取位址檢查。這些模組不得依賴框架、資料庫或儲存。
- **匯入**以注入假抓取的方式測，回傳手寫的樣本頁，不連真實網站。
- **整體流程**用一支瀏覽器冒煙腳本，從畫面走一遍主要流程（登入、新增、照片、面板與返回鍵、狀態、目前結論、留言、貼網址、去重、回收桶）。這是最主要的一道把關。
- 測試用的網頁樣本是手寫的精簡片段，不整頁複製第三方網頁。
- 程式庫目前沒有任何既有測試可參照。

## D. 開發階段與優先順序

優先順序就是下面的先後：階段零 → 階段一（先上線、可使用）→ 階段二（補齊第一版）。B8 的項目不排入。

每一步都要能獨立驗證再往下走。括號內的編號是該步驟主要完成的項目；跨步驟才驗得了的項目在階段結束時確認。每個階段結束時的關卡相同：AC30 通過、冒煙腳本通過、該階段的驗收標準逐條確認。階段零的關卡只有 AC30。

### D1. 階段零：準備（授權後、寫功能前）

1. 建立專案骨架：Next.js、Tailwind、lint／型別檢查／測試指令、`vercel.json` 區域、全站 noindex 標頭、`.env.example`。
2. 本機資料庫與 schema 腳本可重複執行。
3. `lib/storage.ts` 與本機磁碟模式可用。

### D2. 階段一：可上線可用

依序完成：

1. 進出控制：登入頁、session、`proxy.ts`、`verifySession()`、登出。（AC1–AC3）
2. 物件基本流程：手動新增、圖庫、狀態篩選、詳細面板、網址狀態與返回鍵、上一間／下一間、編輯欄位、Google Maps 與原始刊登連結。（AC5、AC13、AC16、AC17、AC19–AC21、AC28）
3. 討論：狀態切換與狀態異動、目前結論、留言與草稿保留。（AC22–AC24）
4. 照片：瀏覽器壓縮、上傳、封面、刪除、輪播、全螢幕大圖、縮圖。（AC14、AC15、AC18、AC29）
5. 刪除與回收桶。（AC27）
6. 貼網址新增：取網址、去重鍵（含全部 591 規則與短連結）、建立物件、安全抓取、通用解析。（AC7、AC9–AC12、AC32）
7. 分頁回到前景自動更新、空白狀態、錯誤訊息、手機版檢查。（AC4）
8. 冒煙腳本與階段一驗收；取得部署授權後依 D4 上線。（AC6）

### D3. 階段二：補齊

1. 591 店面出租頁的進階解析與整組照片。（AC8）
2. 列表檢視。（AC25）
3. 搜尋與排序。（AC26）
4. 全部驗收標準 AC1–AC34 逐條確認；取得授權後更新正式站。

### D4. 上線步驟

「大哥」是只有帳號擁有者能做的步驟；「代理」是開發代理在取得授權後可代勞的步驟。

| 步驟 | 誰 | 內容 |
|---|---|---|
| 1 | 大哥 | 確認 Vercel 方案（A3 第 1 點），並授權部署，包含建立與推送 `main` 分支。A3 第 2、3 點已採預設，不需回覆。 |
| 2 | 代理 | 從通過階段一驗收的版本建立 `main` 分支，並確認它存在。代理沒有權限時，請大哥在 GitHub 的分支選單從開發分支建立。 |
| 3 | 代理 | 建立連結此 repo 的 Vercel 專案，**先不部署**；確認正式分支是 `main`、保護設定是 Standard Protection。從這一步到步驟 7 之前，不推送任何分支。 |
| 4 | 大哥 | Vercel 後台 Storage › Create Database › Neon：接受條款、區域選新加坡、關閉 Auth、方案選 Free；連接專案時維持預設（Production＋Preview），不勾 Preview Branching。 |

| 11 | 大哥 | 用私人管道把網址與共享密碼交給股東。 |

專案連上 Vercel 之後，每次推送開發分支都會自動產生一個預覽部署，並對同一個資料庫套用 schema（只增不減，所以安全）。更新正式站一律是把驗收過的版本推進 `main`，需要大哥授權。

### D5. 尚未解決的問題與已知限制

**尚未解決、要等實作或上線才能確認的技術問題**

- **591 在正式主機上是否抓得到。** 實測來自一個美東雲端位址、少量樣本；Vercel 新加坡節點的結果可能不同，591 也隨時可能改版或加防護。上線後第一件事是在正式站貼一個 591 網址確認。抓不到時退回人工補填，網站仍可用。
- **591 App「分享」複製出來的實際文字。** 沒有取得樣本，短連結規則是依網頁內的分享資料推得。若實際格式不同，物件仍會建立，只是去重可能失效。需要大哥日後提供一則樣本。
- **開發代理能否自行完成上線步驟。** 建立 `main` 分支、建立 Vercel 專案與 Blob store、觸發部署這幾項工具都還沒實際呼叫過；D4 已為每一項寫明由大哥在後台操作的退路。
- **新版 Next.js 的預設行為。** 腳手架預設開啟的 Cache Components 若卡住進度，直接關閉（開發指令已寫明）。
- 好房、住商、中信、東森四站沒有測到有效刊登，能否自動帶入要上線後貼真實連結才知道。

**已知限制（設計上的取捨，不是缺陷）**

- 匯入只跑一次。階段一建立的 591 物件只有名稱、描述與封面，階段二上線後不會自動補齊，要手動補填。匯入當下若剛好失敗，也只能手動補填。
- 目前結論以最後寫入者為準。兩位股東同時編輯時，先存的內容會被後存的蓋掉，畫面只會顯示最後更新者。
- 留言送出後不能修改或刪除。
- 同一則刊登若以兩種完全不同的網址形狀貼入，可能建出兩個物件，由股東自行刪除其一。
- 縮圖來源允許任何公開的 Vercel Blob store。知道本站網域的外人理論上可以借用縮圖功能處理別的 store 的圖片，影響僅止於用量，由用量預算把關。
- Neon Free 的時間點還原只有 6 小時。軟刪除與回收桶是主要的防呆。
- 共享密碼沒有鎖定機制，安全性取決於密碼長度與是否外流。
- repo 若改為私人，由開發代理身分提交的版本可能被 Vercel 擋下不自動部署，需改用部署工具或後台觸發。
- Vercel 與 Next.js 的價格、限制、預設值變動快，本規格書的數字是 2026-11-20 的狀態。
